THE MAP SCREEN — the spec hole is closed.

  Built in the §9.6 material language, not as a menu: the same squared paper,
  the same wooden tray, the same navy plates, the one gold accent. A level is a
  hexagonal plate — the same object the lane queues — so the map reads as the
  same desk seen from further back.

  Progression is strictly linear and NOT star-gated. §8.1's fairness contract
  says the ladder is the difficulty curve; a star toll on top would be a second
  curve the player cannot see, which is the same objection as hidden difficulty
  adjustment. Cleared levels stay open forever so stars can be improved (§5.4).

  Unlocks per §7.6, absent rather than greyed: lives at 2-8, shop at 3-6, modes
  cleared 3-10, and the map itself at cleared 1-10 — so the "map" button on the
  board is also absent until then. 9 tests cover the disclosure schedule.

  ONE JUDGEMENT CALL, flagged: locked LEVELS are dimmed, not absent. §7.6's
  absent-before-unlock rule is about systems the player has no use for yet, and
  seeing that there are forty levels is the entire point of a map. Say if you
  want them hidden instead.

1. CAPACITOR ANDROID
   appId com.nadavw.lanemath, portrait locked in the manifest. Took Capacitor
   core/android/cli and the AdMob community plugin only — not lane-defense's
   haptics or anything else it happened to have.

2. ADMOB — rewarded video only, for the §5.2 life refill. No interstitials.
   Test ids throughout: app id ca-app-pub-3940256099942544~3347511713 in the
   manifest, rewarded unit ...~/5224354917 in src/ads/ads.ts. Production ids
   replace those two constants and nothing else.

   The plugin is INJECTED, so the reward logic is testable without a device —
   which matters, because the failure paths are what a device test skips. 6
   tests: grants only on a real reward callback; a dismissal grants nothing and
   COSTS nothing; no fill degrades to unavailable; absent entirely on web.

   Two economy rules worth stating. An ad life is capped at the normal ceiling,
   so ads buy TIME, not an advantage — that keeps them outside §8.1. And it does
   not move the regeneration anchor, or an ad would silently cancel the free
   refill the player was already waiting for.

3. TELEMETRY REMOTE SINK — NOT ADDED, seam intact, and here is why.
   §12's zero-cost rule rules out the realistic options. Every managed analytics
   endpoint that would fit this game (a few events per session, 40 levels)
   either needs an account with a paid tier behind it, or is a third-party SDK
   with its own bundle and privacy cost — which for an offline single-player
   puzzle buys nothing a local funnel does not already give. A self-hosted
   endpoint is not zero-cost either; it is a server to keep alive.
   TelemetrySink is a one-method interface and LocalStorageSink already
   implements it, so adding a remote one later is a file, not a refactor. I have
   not added a dependency to hold that open. Tell me if you have an endpoint.

4. CI/CD — .github/workflows/ci.yml. Typecheck, then the three named gates
   (brightness, retry path, flight bound) run individually so a failure names
   ITSELF in the log rather than arriving as "1 of 270 tests failed", then the
   full suite, then build, then Pages deploy on master only. Branch pushes run
   every gate and never publish.

   NOT VERIFIED GREEN ON GITHUB — this repo has no remote configured, so nothing
   has been pushed and no run exists. Every step was run locally and passes.
   That is a real gap and I am not going to call it green.

5. SIGNED RELEASE APK — 3.75 MB (3,933,178 bytes).
   Signed with the existing keystore (CN=Lane Defense), R8 + shrinkResources on.
   Keystore, keystore.properties and local.properties are all gitignored and
   confirmed untracked.

   What is actually in it:
     classes.dex           4,906,156 uncompressed  <- Play Services Ads is most
     web bundle (js)       ~  850,000
     backgrounds (4 webp)  ~  395,000
     resources.arsc           509,448
   The Java side dominates, not the game. Dropping AdMob would save more than

6. BUNDLE — measured before changing anything, as asked.

   PixiJS share, measured by building the whole game against a stub Pixi:
     game code only    407,031 raw /  52,805 gz
     with PixiJS       958,905 raw / 215,014 gz
     PIXI              551,874 raw (57.6%) / 162,209 gz (75.4%)

   So over the wire Pixi is three quarters of it, and your instinct was right.
   But two things temper what tree-shaking can recover:
     - It is ALREADY a production build with the renderers code-split. WebGPU
       (38.9 KB raw / 10.9 KB gz) and WebGL (68.7 / 18.8) are separate lazy
       chunks; only the one the device uses loads. The 688 KB index chunk is
       Pixi CORE plus the game, and Pixi v8's core is not meaningfully
       subsettable through the public entry points.
     - Dev-only deprecation strings ARE still in the bundle, so a genuinely
       production Pixi build is not being selected. That is a real finding and
       the first thing to try — but I have not measured what it saves, and I am
       not going to quote a number I have not run.

   THE BIGGER LEVER IS NOT PIXI. The 40 level JSON files are 560 KB on disk and
   ship whole. Only 10.8 KB of that is fields the game reads — pool, targets,
   rules, budgets. The other 549 KB is generator and curation METRICS
   (keystones, decisionPoints, survivalRate, temptation scores) that no runtime
   code touches. Stripping them at build time:
     raw      349,971 -> 10,853   saves 339,118  (a third of the whole bundle)
     gzipped   19,511 ->  1,471   saves  18,040
   Compressed it is worth less than Pixi; uncompressed — which is what the APK
   and the parse cost care about — it is the single biggest item after Pixi
   core, and it is dead weight rather than a tradeoff. Not done: you said report
   before changing.
