  YOUR PRIOR IS DISPROVED, and cleanly: ticker listeners are flat at 2 for the
  whole run. Nothing registers a callback per effect. Every tween collection is
  also flat — lifts, rewrites and starArrivals all self-prune correctly. The one
  thing that grows is `flights`, and rootChildren tracks it exactly, because
  every live flight draws one extra token on every redraw.

  CAUSE: flights was a plain array, appended to on every placement and pruned
  ONLY inside the ticker callback. Tap cost is linear in flights because
  drawFlights() walks it every redraw.

  TRIGGER, and this matters for how to read the numbers: the benchmark drives
  input in a tight synchronous loop, so no frame is ever delivered, so the
  pruning never runs. Re-measured with a requestAnimationFrame yield between
  taps, the SAME pre-fix build is flat at 1.0ms with flights plateauing at
  12-15. So a player tapping at human speed never saw this. What the code had
  was not "slow", it was "correct only while frames keep arriving" — which a
  background tab, a long GC or a slow device all break.

THE FIX — bounded by construction, not by the ticker.

  flights is now keyed by SLOT (src/renderer/flights.ts). A slot holds one thing
  at a time, so it can have at most one token travelling to or from it, and there
  are three slots. The collection cannot exceed three however input arrives, and
  a new flight for a seat supersedes the stale one instead of stacking a second
  identical token on top of it — which was a second, quieter bug in the same
  code: rapid taps on one slot drew overlapping tokens.

  The fix removes the dependency on frame delivery rather than making pruning
  more frequent. Nothing has to be trusted for it to hold.

  AFTER, same tight 600-tap loop that produced 35.6ms:

  median ms       0.5    0.5    0.5    0.5     flat
  flights           1      1      1      1     flat
  rootChildren     22     22     22     22     flat
  heap MB        56.6   81.3  107.1  145.3     normal churn, was 3751

REGRESSION TEST — src/renderer/flights.test.ts, 7 tests.
  Deliberately NOT a millisecond assertion: that would be machine-dependent and
  flaky, and it would pin the symptom. It asserts the quantity that DRIVES the
  latency — the number of flights, which is the per-redraw draw work — stays
  bounded no matter how much input arrives, with the clock never advanced,
  because that is the exact failing condition. 600 taps with no frame in
  between: size stays 1. That is the machine-independent form of "600 taps costs
  what 100 taps costs".

STRAIGHT-RUN A/B — independent confirmation, no interleaving.

  order 1:  audio on 0.7ms   then muted 0.4ms
  order 2:  muted 0.5ms      then audio on 0.7ms

  Audio on is now consistently ~0.25ms slower than muted, in BOTH orders. That
  is causally sensible — scheduling oscillator nodes costs something — and it no
  longer depends on which series ran first.

  Before the fix the same straight run gave audio-on 1.4ms and muted 2.5ms:
  muted measuring SLOWER than unmuted, which is impossible. You were right that
  the drift I worked around WAS the bug. The interleaving last session was a
  correct workaround for a real defect and a wrong thing to settle for.

  Honest number: audio costs about 0.25ms per tap, on a 16.7ms frame budget.
